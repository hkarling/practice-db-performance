# LOG007 — batch size 설정과 fetch join의 트레이드오프

## 배경 / 목표

Phase 2 챕터 7. LOG005(N+1)와 동일한 코드(`NPlusOneTest`)를 전혀 수정하지 않은 채,
`hibernate.default_batch_fetch_size` 설정만 추가해서 SQL 패턴이 어떻게 바뀌는지
확인하고, fetch join(LOG006)과의 트레이드오프를 비교한다.

## 개념

### `default_batch_fetch_size`
Hibernate가 LAZY 연관관계를 **개별 쿼리 대신 `IN`(Postgres는 `= ANY(배열)`) 절로
묶어서** 조회하게 하는 설정. fetch join과는 동작하는 레이어 자체가 다르다:

- **fetch join**: "이 쿼리를 실행할 때 조인해서 가져와라"는 **쿼리 작성 시점**의 지시.
  쿼리 코드를 직접 고쳐야 한다.
- **batch fetch**: "나중에 이 타입의 LAZY 프록시가 초기화될 때, 같은 타입의 미초기화
  프록시가 여러 개 있으면 한꺼번에 묶어서 가져와라"는 **프록시 초기화 시점**의 지시.
  어떤 쿼리가 부모 엔티티를 가져왔는지와 무관하게 동작한다.

이 차이 때문에 batch fetch는 **쿼리/리포지토리 메서드 단위로 지정할 수 없다** —
항상 엔티티(또는 컬렉션 필드) 단위(`@BatchSize`) 또는 전역 단위
(`default_batch_fetch_size`)로만 설정 가능하다. 이번엔 이 프로젝트에 LAZY
연관관계가 `Order.customer` 하나뿐이라 어느 쪽으로 설정해도 결과가 동일해서, 더
간단한 전역 설정으로 진행했다.

**실무에서도 전역 설정이 기본값에 가깝다.** N+1은 특정 엔티티만 골라서 걸리는 문제가
아니라 프로젝트 전체 LAZY 연관관계에 공통으로 적용해도 손해가 거의 없는 안전망이라,
코드 변경도 엔티티마다 애노테이션을 붙이고 다닐 필요도 없이 설정 한 줄로 끝나는
전역 프로퍼티를 기본으로 깔아두는 경우가 많다. `@BatchSize`는 전역값과 다르게
가져가야 하는 예외 케이스(예: 유난히 자주 조회되는 컬렉션은 더 크게, 거의 안 쓰이는
무거운 연관관계는 더 작게)에 대한 오버라이드로 쓰는 경우가 많다.

### 설정

```yaml
spring:
  jpa:
    properties:
      hibernate:
        format_sql: true
        default_batch_fetch_size: 10
```

## 진행 내용

`NPlusOneTest.java`는 LOG005와 완전히 동일한 코드를 그대로 재사용했다 — 코드 변경 없이
설정 하나만으로 SQL이 어떻게 달라지는지 보는 게 목적.

### 결과 — SQL

```sql
select
    c1_0.id, c1_0.city, c1_0.created_at, c1_0.email,
    c1_0.name, c1_0.state, c1_0.updated_at, c1_0.zip_code
from
    customers c1_0
where
    c1_0.id = any (?)
```

바인딩: `[[357807, 547801, 920039, 99100, 48135, 234429, 156376, 925499, 299463, 168965]]`
(customer_id 10개를 배열 하나로 바인딩)

**해설**
- 20건의 customer 접근에서 개별 `SELECT`가 아니라 **정확히 2번**(`ceil(20/10)=2`)의
  batch 쿼리만 나갔다. `2-1` 접근 시점에 첫 배치(10개)가, `2-11` 접근 시점에 두 번째
  배치(10개)가 나갔다 — 나머지(`2-2`~`2-10`, `2-12`~`2-20`)는 이미 채워진 상태라 SQL
  로그가 안 찍혔다.
- **왜 `2-1` 접근 시점에 이미 10개를 가져왔나**: `findAll()`로 주문 20건을 가져올 때
  Hibernate는 각 주문의 `customer` 필드에 **미초기화 프록시 20개를 전부 미리 등록**해
  둔다. 그중 하나(`2-1`)라도 실제로 건드리면, "같은 타입의 미초기화 프록시가 영속성
  컨텍스트에 몇 개나 더 있나"를 확인해서 batch size만큼 한꺼번에 채운다 — 접근한 순서가
  아니라 프록시가 등록된 순서(= 주문 결과 순서) 기준으로 묶인다.
- Postgres 방언이라 `IN (?,?,...)`가 아니라 `= ANY(배열)` 형태로 나간다. 기능은
  동일하지만 바인딩 파라미터가 개별 값이 아니라 배열 하나(`ARRAY` 타입)로 묶인다.
- 최종 쿼리 수: `1(주문 목록) + 1(count) + 2(batched customer) = 4번`.

### 실행 시간 비교

| | 쿼리 수 | 실행 시간 |
|---|---|---|
| N+1 (설정 전, LOG005) | 22 | 0.769s |
| batch fetch (`default_batch_fetch_size: 10`) | 4 | 0.646s |
| fetch join (LOG006) | 1 | 0.7s |

쿼리 수는 22 → 4 → 1로 계속 줄었지만 실행 시간은 계속 0.6~0.8초대에 머물렀다(오차
범위 안에서 뒤섞임). LOG006에서 확인한 "이 스케일/로컬 환경에서는 쿼리 수가 유일하게
신뢰할 수 있는 구조적 지표"라는 결론이 다시 확인됐다.

## 트레이드오프 — batch fetch vs fetch join

| | fetch join | batch fetch |
|---|---|---|
| 쿼리 수 | 정확히 1 | `ceil(N / batch size)` |
| 코드 변경 | 쿼리마다 `JOIN FETCH` 직접 작성 | 설정만 추가, 기존 쿼리 코드 무변경 |
| 적용 범위 | 그 쿼리 하나에만 | 프로젝트 전역(또는 엔티티 단위)에 자동 적용 |
| to-many + 페이지네이션 | 위험 (cartesian product로 `LIMIT`이 깨짐) | 안전 (컬렉션도 별도 배치 쿼리로 처리) |
| 여러 컬렉션 동시 fetch join | `MultipleBagFetchException` 위험 | 문제없음 (각 컬렉션이 독립적으로 배치됨) |
| 튜닝 여지 | 없음(항상 1) | batch size로 "쿼리 수 vs 각 쿼리의 `IN` 배열 크기" 조절 가능 |

**결론**: fetch join은 "이 화면에서 반드시 필요한 특정 조회"에 대해 쿼리 수를 최소로
줄이는 정밀 도구, batch fetch는 "프로젝트 전체 LAZY 연관관계에 대한 안전망"에
가깝다. 실무에서는 보통 **batch fetch를 전역 기본값으로 깔아두고, 성능이 중요한
특정 조회에만 fetch join을 선택적으로 추가**하는 조합을 많이 쓴다 — 이번 프로젝트도
이 조합을 그대로 채택했다(전역 batch size + `OrderRepository.findAllWithCustomer`는
fetch join 유지).

## 시행착오 / Q&A

**Q. batch size를 크게 잡으면(예: 1000) 무조건 좋은 거 아닌가?**
A. 쿼리 수는 줄지만 `IN`/`ANY` 배열이 그만큼 커진다 — 매우 큰 배열은 DB 쪽 파싱/실행
비용이 늘고, 실제로 해당 배치 크기만큼 프록시가 쌓여있지 않으면(예: 5건만 조회했는데
batch size 1000) 이득도 없다. N+1 정도만 해소하면 되는 상황이라 이번엔 10으로
설정했고, 최적값은 실제 화면의 조회 규모에 맞춰 조정 대상.

**Q. 적절한 batch size는 어떻게 정하나?**
A. 정해진 정답은 없고, 판단 기준은 이렇다.
- **실제 조회 규모에 맞춘다**: "보통 한 화면/한 요청에서 몇 건을 가져오는가"가 가장
  실용적인 기준. 이 프로젝트는 `PageRequest.of(0, 20)`처럼 페이지당 20건을 자주
  다루므로, 운영값으로는 20~25 정도로 잡으면 일반적인 경우 배치 1번으로 페이지
  전체가 커버된다. 지금 10으로 둔 건 "20건 → 2번의 배치"를 눈으로 확인하기 좋은
  실습용 값.
- **한계 이득 체감**: 22 → 4로 줄이는 것(쿼리 하나당 왕복을 없애는 것)이 대부분의
  이득이고, 4 → 1로 줄이는 추가 이득은 상대적으로 작다. 그래서 흔히 보이는 실무값은
  10~50 사이 — 극단적으로 크게(수백~수천) 잡는 경우는 드물다.
- **(참고) 실행계획 캐시**: batch size로 안 딱 떨어지는 나머지(예: 20건을 13, 7로
  나눠 배치)는 `IN` 절 크기가 달라 DB가 다른 모양의 SQL로 인식해 실행계획 캐시를
  재활용 못 할 수 있다. Hibernate 버전별로 이를 완화하는 전략(패딩 등)이 있는데,
  이번 챕터에선 세부 메커니즘까지 검증하지 않았다 — 필요시 추후 별도 확인.

## 최종 구성

| 파일 | 변경 |
|---|---|
| `src/main/resources/application.yaml` | `hibernate.default_batch_fetch_size: 10` 추가 |

`NPlusOneTest.java`, `FetchJoinTest.java`는 변경 없음 — 코드 재사용 자체가 이번
실험의 핵심.

## ADR

### Decision
- 전역 `default_batch_fetch_size: 10`을 기본 안전망으로 깔아두고, 특정 쿼리에서 쿼리
  수를 정확히 1로 줄여야 할 필요가 있으면 그때 fetch join을 선택적으로 추가한다.

### Drivers
- fetch join은 쿼리마다 직접 작성해야 하고 to-many + 페이지네이션 조합에서 위험할 수
  있어, 프로젝트 전체를 fetch join만으로 커버하기 어려움 — batch fetch로 전역
  안전망을 깔아두는 게 실무적으로 더 견고함

### Alternatives considered
- 엔티티별 `@BatchSize` — 현재는 LAZY 연관관계가 `Customer` 하나뿐이라 전역 설정과
  결과가 동일. 향후 연관관계가 늘어나 엔티티별로 다른 batch size가 필요해지면
  재검토할 대상으로 남겨둠(예: 자주 조회되는 연관관계는 크게, 드문 건 기본값 유지)

### Consequences
- batch fetch는 "쿼리 수를 줄이는 것"이지 "N+1을 0으로 만드는 것"은 아니다(N/batch
  size로 줄어들 뿐) — 완전히 1번으로 줄여야 하는 핫패스는 여전히 fetch join이 필요
- 전역 설정이라 앞으로 추가되는 모든 LAZY 연관관계에 기본 적용됨 — 별도 설정 없이도
  안전망이 작동

  쿼리를 QueryDSL로 다시 작성해 비교)
